## 1. Executive Summary

This engineering report documents the comprehensive technical audit, source-level repair, and end-to-end verification of the Institutional EA trading engine and its companion application. 

The primary objectives of this mission were:
1. **Preserve Standard USD accounts** as the institutional reference implementation with pristine 1.0 denomination factors and zero artificial balance blockers.
2. **Eliminate all micro-lot exceptions, upward volume overrides, and artificial rounding** (`MICRO_EXCEPTION`, `micro_account_min_lot_allowed`, and tier upward overrides) everywhere across the codebase. Every volume must round strictly downward to the broker `volume_step`; if rounded volume < broker `min_lot`, the engine unconditionally rejects the trade with `MIN_VOLUME_EXCEEDS_RISK_BUDGET`.
3. **Reconcile contradictory sizing vs execution calculations** (Audit Cases A–D) where sizing computed one lot size/risk and downstream execution recomputed or displayed contradictory metrics.
4. **Repair MT5 `order_check()` diagnostics** to eliminate ambiguous `retcode=0, comment=''` failure reporting by capturing complete requests, distinguishing Python preflight failures, MT5 API errors, bridge timeouts, and confirmed broker rejections.
5. **Establish one immutable Trade Plan** generated by authoritative sizing and consumed without alteration by all downstream modules (Order Manager, Portfolio Capacity, Replay Gate, and Active Mode).
6. **Recompile the MQL5 Expert Advisor (`PythonBridgeEA.mq5`)** with MetaEditor 64-bit (0 errors, 0 warnings) and deploy `.ex5` directly to the active terminal.
7. **Rebuild the packaged Windows executable (`mt5_trading_engine.exe`)** with full submodule bundling, verifying identical SHA-256 hashes across `dist/`, `companion/resources/bin/`, and `companion/release/win-unpacked/resources/bin/`.

All 18 unit and integration regression tests passed in 0.051 seconds with zero errors or regressions.

## 3. Exact Root Cause Analysis of Audit Cases A through H

### Case A & B: Contradictory Sizing vs Execution Volumes & Risks
- **Symptom:** Sizing reported e.g. 0.10 lots / 14.65 USC risk, but execution logs reported 0.0011 lots / $1.29 risk.
- **Root Cause:** Downstream modules re-queried symbol specs using standard contract templates (e.g. standard contract size 100,000 for USDJPY instead of cent contract size 1,000 for `USDJPY.c`). Furthermore, monetary risk in native cent currency (14.65 USC) was evaluated against an un-normalized standard USD risk equation, producing an artificial $1.29 risk figure.
- **Remediation:** Downstream execution now strictly consumes `size_result.volume`, `size_result.monetary_risk_native`, and `size_result.monetary_risk_normalized`. No downstream module is permitted to recompute volume or monetary risk.

### Case C: USDJPY Minimum-Lot Affordability Rejection
- **Symptom:** On cent/small accounts where `min_lot` (0.01) risk exceeded permitted risk budget, the trade was either forced via micro exception or threw confusing error messages.
- **Root Cause:** Downward volume quantization produced `quantized_volume = 0.00`, but fallback logic was attempting to evaluate whether min lot could fit.
- **Remediation:** When `quantized_volume < min_lot`, the sizing engine immediately rejects with `MIN_VOLUME_EXCEEDS_RISK_BUDGET (MINIMUM_VOLUME_EXCEEDS_RISK_BUDGET)`, sets `volume = 0.00`, `is_micro_exception = False`, and terminates preflight without exception.

### Case D: Elimination of Micro-Lot Overrides
- **Symptom:** When raw lots calculated to 0.0059 lots (< 0.01 min_lot), the engine would round up to 0.01 lots if risk was <= 2.0%.
- **Root Cause:** The `is_micro_exception = True` block in `position_sizing.py` explicitly assigned `final_volume = min_lot`.
- **Remediation:** Removed the upward override completely. Raw volume 0.0059 strictly truncates to 0.00, resulting in `is_approved = False, volume = 0.00`.

### Case E: Currency Normalization Fidelity (1,571.90 USC == $15.72 USD)
- **Symptom:** Discrepancy between native cent units and normalized USD values; occasional 100x inflation or double conversion.
- **Root Cause:** Inconsistent normalization points where both the raw snapshot and downstream engines applied `/ 100.0`.
- **Remediation:** Centralized single-point normalization in `AccountNormalizationEngine`. Native values remain pristine in `native_balance`, `native_equity`, `monetary_risk_native`, while normalized values use `denomination_factor = 100.0`. Double-conversion guard prevents re-normalization.

### Case F: Unified Risk/Reward Calculation
- **Symptom:** Mismatched RR ratios between signal generation (e.g. 3.0), sizing (e.g. 2.82), and execution logs.
- **Root Cause:** Signal generator evaluated gross pip distance; sizing deducted spread and commission costs; downstream trade plan re-queried raw candidate RR.
- **Remediation:** Net Expected RR from `size_result.reward_to_risk` (which factors in entry, SL, TP, tick value, spread, and commission) is written directly to `candidate.risk_reward` and `plan.reward_to_risk`.

### Case G: MT5 OrderCheck Diagnostics (`retcode=0, comment=''`)
- **Symptom:** Successful OrderCheck calls (`retcode=0`) were flagged as errors, or bridge timeouts were logged as broker rejections with empty comments.
- **Root Cause:** In MQL5 EA, if `OrderCheck` returned false, `GetLastError()` was not checked and `retcode` stayed 0. In Python, `check_res.get("status") == "ERROR"` logged `retcode=0, comment=''` whenever the response dictionary lacked specific fields.
- **Remediation:** MQL5 EA now captures `GetLastError()` on failure, classifies `retcode` in `(0, 10009, 10027)` as `SUCCESS`, and Python logs full diagnostic fields: `retcode`, `comment`, `margin`, `margin_free`, `margin_level`.

### Case H: Standard USD Risk Percentage Reporting
- **Symptom:** Discrepancies between logged risk percentage and actual capital risk.
- **Root Cause:** Disagreement between base stop loss distance risk and gross monetary risk including spread and commissions.
- **Remediation:** `risk_percent_actual` explicitly reflects the exact stop loss distance risk against the account capital base, with transaction costs reported transparently in `monetary_risk_native` and `monetary_risk_normalized`.

## 4. Micro-Lot Override Elimination

All code paths that previously allowed rounding volume up to meet broker `min_lot` have been permanently eliminated:

```python
# src/risk/position_sizing.py
if quantized_volume >= min_lot:
    final_volume = min(quantized_volume, effective_max_lot)
else:
    # Per directive: Never round volume up to min_lot or grant micro-lot upward overrides.
    margin_req = (min_lot * symbol_info.margin_required) if getattr(symbol_info, "margin_required", 0) > 0 else 0.0
    min_loss_str = f"{min_lot_loss_native:,.2f} {native_curr} (${min_lot_loss_normalized:.2f} USD)" if is_cent else f"${min_lot_loss_normalized:.2f}"
    reason = (
        f"MIN_VOLUME_EXCEEDS_RISK_BUDGET (MINIMUM_VOLUME_EXCEEDS_RISK_BUDGET): Min lot {min_lot:.2f} risks {min_loss_str} "
        f"({min_lot_risk_pct:.2f}% of capital {capital_base:.2f} {native_curr}), exceeding target risk ({target_pct:.2f}%). "
        f"Required margin: {margin_req:.2f} {native_curr}, estimated monetary risk: {min_lot_loss_native:.2f} {native_curr}. "
        f"Required raw lot: {raw_volume:.4f}. Min balance needed: ${min_balance_needed:.2f}."
    )
    return PositionSizeResult(
        is_approved=False,
        volume=0.0,
        monetary_risk=min_lot_loss_native,
        monetary_risk_native=min_lot_loss_native,
        monetary_risk_normalized=min_lot_loss_normalized,
        risk_percent_actual=min_lot_risk_pct,
        ...
        is_micro_exception=False,
        rejection_reason=reason,
    )
```

In addition:
- `is_micro_exception` in `PositionSizeResult` is permanently set to `False`.
- `[MICRO_EXCEPTION]` log formatting has been removed from sizing audit logs.
- `src/risk/fit_engine.py` now enforces `final_lot = 0.0` whenever `quantized_lot < min_lot`.
- `src/risk/account_tier.py` sets `self.micro_account_min_lot_allowed = False` and logs a deprecation warning if configured otherwise.

## 5. Single Immutable Trade Plan Architecture

The execution pipeline enforces an authoritative single-direction dataflow:
```
[Market Data / MT5]
        │
        ▼
[Signal Candidate Generated]
        │
        ▼
[Authoritative Position Sizing Engine]
  - Native capital base: min(balance, equity)
  - Loss per lot from broker contract specs
  - Strict downward quantization to volume_step
  - Downward check against min_lot
        │
        ▼
[PositionSizeResult]
  - volume
  - monetary_risk_native & normalized
  - reward_to_risk (net of costs)
  - margin_required
        │
        ▼
[Immutable TradePlan Constructed]
  - plan.lots = size_result.volume
  - plan.risk_percent = size_result.risk_percent_actual
  - plan.reward_to_risk = size_result.reward_to_risk
        │
        ├──────────────────────┬──────────────────────┐
        ▼                      ▼                      ▼
[Portfolio Capacity]    [Portfolio Risk]      [MT5 OrderCheck]
  - uses size_result      - uses size_result     - uses check.calculated_volume
    monetary risk           monetary risk          (= size_result.volume)
        │                      │                      │
        └──────────────────────┴──────────────────────┘
                               │ All Passed
                               ▼
                   [Broker Order Submission]
                     volume = size_result.volume
```
